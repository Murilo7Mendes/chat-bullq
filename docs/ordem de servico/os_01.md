# OS-01: Base de Conhecimento (FAQ) + Calendário de Feriados para Agentes de IA

**Status**: Planejada
**Criada em**: 2026-08-21
**Prioridade**: Alta

---

## Contexto

Os agentes de IA do Chat BullQ já possuem uma pipeline RAG completa (embeddings OpenAI, pgvector, retrieval por similaridade coseno), porém ela só indexa **mensagens de conversas passadas** — funciona como memória de longo prazo do agente. Não existe mecanismo para subir documentos estáticos (FAQ, manuais, tabelas fiscais) que o agente consulte ao responder perguntas técnicas.

### Problema

Clientes de escritórios de contabilidade fazem perguntas frequentes como:
- "Qual prazo eu tenho para fazer o pagamento da folha?"
- "Qual o CFOP para fazer devolução?"
- "Qual a data de vencimento do DAS?"
- "Quando vence o FGTS?"

Essas perguntas precisam de dois tipos de resposta:
1. **Informação estática** (FAQ): regras, prazos legais, códigos fiscais → resolvido por busca semântica em documentos
2. **Cálculo dinâmico**: "qual dia exato?" → depende do calendário de feriados para calcular dias úteis

### O que já existe

| Componente | Status | Localização |
|---|---|---|
| EmbeddingsService (OpenAI text-embedding-3-small) | Pronto | `api/src/modules/ai-agents/rag/embeddings.service.ts` |
| VectorStoreService (pgvector, cosine search) | Pronto | `api/src/modules/ai-agents/rag/vector-store.service.ts` |
| RetrievalService (embed query → search → rerank) | Pronto | `api/src/modules/ai-agents/rag/retrieval.service.ts` |

| Injeção no prompt (augmentSystemPromptWithLayers) | Pronto | `api/src/modules/ai-agents/runner/agent-runner.service.ts` |
| ToolRegistry (tools builtin para agentes) | Pronto | `api/src/modules/ai-agents/tools/tool-registry.service.ts` |
| Tabela `ai_vector_entries` (pgvector) | Pronto | SQL manual (não no Prisma schema) |

### O que falta

- Modelo `AiKnowledgeDocument` no Prisma
- `ownerType: 'document'` no sistema RAG
- API CRUD para documentos de conhecimento
- Chunking de texto longo
- Segunda retrieval no runner (scoped por `agentId` sem `contactId`)
- UI para gerenciar documentos por agente
- Modelo `Holiday` no Prisma
- CRUD + seed de feriados (nacionais/estaduais/municipais)
- Cálculo de n-ésimo dia útil com feriados
- Tool builtin `calcular_dia_util` para o agente
- UI de feriados nas configurações

---

## Decisão Arquitetural

**FAQ**: Reutilizar 100% da infra RAG existente. Documentos vão na mesma tabela `ai_vector_entries` com `ownerType: 'document'`. Uma segunda retrieval dedicada busca por `agentId + ownerType='document'` (sem `contactId`/`conversationId`, que filtraria os docs fora pelo AND do pgvector).

**Feriados**: Nova tabela `holidays` com CRUD + lógica de cálculo de dias úteis. Tool builtin `calcular_dia_util` registrada no `ToolRegistry` — o agente pode chamá-la durante o loop de tool calls quando o cliente pergunta por datas.

### Etapa 2 — Chunking + Embeddings (indexação automática)

**Entrega**: ao criar ou editar um documento, o sistema automaticamente quebra o texto em chunks, gera embeddings via OpenAI e salva no pgvector.

#### Arquivos novos
- `api/src/modules/ai-agents/rag/chunker.ts` — função de chunking

#### Arquivos modificados
- `api/src/modules/ai-agents/rag/types.ts` — `'document'` no VectorOwnerType + variant `index_document` no IndexerJobData
- `api/src/modules/ai-agents/rag/indexer.processor.ts` — case `index_document`
- `api/src/modules/ai-agents/knowledge/knowledge.service.ts` — no create/update: chunkar → enfileirar; no remove: deletar entries

#### Lógica de chunking

```
Texto original → split por \n\n (parágrafos)
  → se parágrafo > 800 chars, split por frases (". ")
  → chunks de ~800 chars com 100 chars de overlap entre vizinhos
  → IDs: "document:{docId}:chunk:{index}"
```

#### Lógica do indexer

```
Job index_document recebido
  → deletar entries antigas: DELETE FROM ai_vector_entries WHERE owner_type='document' AND owner_id LIKE 'document:{docId}:%'
  → embeddings.embedBatch(chunks.map(c => c.content))  // 1 API call
  → upsert cada chunk no vector store com ownerType='document', agentId do scope
  → atualizar doc: status='ready', chunkCount=N
```

#### Verificação

```sql
-- Após criar documento com texto longo:
SELECT id, owner_type, LEFT(content, 80) AS preview, agent_id
FROM ai_vector_entries
WHERE owner_type = 'document' AND agent_id = '{agentId}';
-- → retorna N chunks
```

### Etapa 3 — Retrieval de documentos no prompt do agente

**Entrega**: quando o cliente envia uma mensagem, o runner do agente busca chunks relevantes da base de conhecimento e injeta no system prompt, junto com o RAG de histórico existente.

#### Arquivo modificado
- `api/src/modules/ai-agents/runner/agent-runner.service.ts` — no `augmentSystemPromptWithLayers()`

#### Lógica

Após o RAG de histórico existente (etapa 2 do método), adicionar:

```typescript
// 3) Knowledge base retrieval (só agentId, sem contactId/conversationId)
let knowledgePart = null;
if (triggerText?.length >= 5) {
  try {
    const docResults = await this.retrieval.retrieve({
      query: triggerText,
      scope: { agentId, ownerType: 'document' },
      k: 5, minScore: 0.72,
    });
    if (docResults.length > 0) {
      const lines = docResults.map((r, i) => `${i + 1}. ${r.entry.content}`).join('\n');
      knowledgePart = {
        type: 'text',
        text: `═══ Base de conhecimento ═══\n${lines}\n\nUse essas informações para responder com precisão. Cite dados e bases legais quando relevante.`,
        cache: false,
      };
    }
  } catch (err) {
    this.logger.warn(`Knowledge retrieval failed: ${err?.message}`);
  }
}
```

#### Por que uma segunda retrieval separada?

O RAG existente busca com scope `{ agentId, contactId, conversationId, ownerType: 'any' }`. Os filtros são combinados com AND no SQL do vector store. Documentos FAQ são indexados **sem** `contactId` e `conversationId` (não pertencem a nenhum contato específico), então seriam filtrados fora pela cláusula AND. A segunda retrieval usa `{ agentId, ownerType: 'document' }` — sem contactId — e retorna os documentos corretamente.

### Etapa 5 — Calendário de feriados + Tool `calcular_dia_util`

**Entrega**: tabela de feriados editável nas configurações + tool que o agente chama para calcular datas úteis exatas.

#### Modelo Prisma

```prisma
model Holiday {
  id             String   @id @default(cuid())
  organizationId String   @map("organization_id")
  date           DateTime @db.Date
  description    String
  city           String?
  state          String?  @db.VarChar(2)  // UF
  scope          String   @default("national") // national | state | city
  createdAt      DateTime @default(now()) @map("created_at")

  organization Organization @relation(fields: [organizationId], references: [id])

  @@unique([organizationId, date, city, state])
  @@map("holidays")
}
```

#### Backend — Holiday service

- `list(orgId, year?, state?, city?)` — feriados com filtros
- `create/update/remove` — CRUD
- `seedNationalHolidays(orgId, year)` — popula feriados nacionais:
  - **Fixos**: 01/01 (Ano Novo), 21/04 (Tiradentes), 01/05 (Trabalho), 07/09 (Independência), 12/10 (Aparecida), 02/11 (Finados), 15/11 (Proclamação), 25/12 (Natal)
  - **Móveis**: Carnaval (47 dias antes da Páscoa), Sexta-feira Santa (2 dias antes da Páscoa), Corpus Christi (60 dias após Páscoa) — cálculo da Páscoa via algoritmo de Gauss
- `getNthBusinessDay(orgId, month, year, n, state?, city?)`:
  - Itera dia a dia no mês
  - Pula sábados e domingos
  - Pula feriados (nacionais + estaduais se `state` informado + municipais se `city` informado)
  - Retorna a data do n-ésimo dia útil
- `isBusinessDay(orgId, date, state?, city?)` — verifica se é dia útil

#### Backend — Tool builtin

```typescript
// api/src/modules/ai-agents/tools/builtin/calcular-dia-util.tool.ts
export class CalcularDiaUtilTool implements AiTool {
  name = 'calcular_dia_util';
  description = 'Calcula o N-ésimo dia útil de um mês, considerando feriados. Use para responder "quando vence X" (folha=5º dia útil, FGTS=dia 7, DAS=dia 20, etc).';
  parameters = {
    type: 'object',
    properties: {
      mes: { type: 'number', description: 'Mês (1-12)' },
      ano: { type: 'number', description: 'Ano' },
      n: { type: 'number', description: 'N-ésimo dia útil (ex: 5)' },
      estado: { type: 'string', description: 'UF (ex: SC). Opcional.' },
      cidade: { type: 'string', description: 'Cidade. Opcional.' },
    },
    required: ['mes', 'ano', 'n'],
  };

  async execute(input, ctx) {
    const date = await holidaysService.getNthBusinessDay(...);
    return {
      output: {
        data: '2026-10-07',
        diaSemana: 'quarta-feira',
        descricao: '5º dia útil de outubro/2026',
      },
    };
  }
}
```

Registrar no `ToolRegistry` para ORCHESTRATOR + WORKER.
